# 阈值档案设备归属与新增校验修复

基线：preview / 3c8ed69ae8688fa3d694a20009f8ca411fea8ffe。按批量发现、设计、集中执行、定向验收推进，只处理用户商业级清单之外的两项具体阈值管理缺陷。

| 编号 | 优先级 | 复现结果 | 方案 |
| --- | --- | --- | --- |
| C22 | P1 | 同一老人绑定两台设备，按姓名查阈值只返回主设备；第二台设备的档案没有老人姓名 | 阈值档案经 device.old_id 关联当前老人，不以 oldperson.device_id 主设备引用代替全部设备归属 |
| C23 | P2 | 输入尚未登记的设备编号 999，阈值新增仍返回成功并写入一条孤立档案 | INSERT SELECT 仅从存在的设备创建档案；不存在时不落库，返回业务失败与先登记设备的提示 |

业务假设与范围：监测阈值属于已登记的具体手表；一位老人可以绑定多台手表，主设备引用不代表完整设备集合。已登记但未绑定老人的设备仍可配置阈值。既有孤立档案继续可查询，不删除或清理历史数据。

生产修改仅涉及阈值列表的归属连接和新增档案的存在性判断；分页总数与列表共用同一查询，显示设备的当前老人。未改变主设备选择、阈值范围、配置修改与告警处理流程；不增加迁移、锁开关、权限或基础设施改造。

修复前两条回归均失败：姓名检索 total=1，设备 999 的档案被插入。修复后 MySQL 8.0.46 和 PostgreSQL 17.6 各 5 条相关用例通过：主次设备均可按姓名检索，编辑次设备阈值后实际 hr=130 上报按新上限 140 判断为正常，主设备仍为 1；不存在的设备不落库，登记后的设备能新增，重复新增继续拒绝。另覆盖既有档案字段/日期合同、绑定保留自定义阈值及告警阈值解释。
