# 核心功能缺陷分批修复

基线：preview / 5a5ad4a3ce857ff1a7428bbf930673f4d898a75b。

本轮按“批量发现 → 设计 → 集中实现 → 统一验收”执行。以下 17 项是用户商业级清单未明确列出的具体业务缺陷，不实施该清单中的架构、KMS、审计体系、通知升级、权限模型、CI 体系或多租户条目。此前已完成的五项家属与上报修复见 [独立说明](2026-10-30-family-telemetry.md)，一并纳入本次 PR。

## 排序与实现

| 编号 | 优先级 | 实际触发与错误结果 | 定向解决方案 |
| --- | --- | --- | --- |
| C01 | P1 | 自定义范围为心率 55–75、血压 180–200，80/170 被解释为心率偏低、血压偏高 | 告警详情查询同时读取设备阈值，按当前配置解释；已落入当前范围的历史告警明确标为历史异常 |

| C04 | P1 | 多名老人共用手机号，添加家属任意关联第一份档案 | 事务内最多读取并锁定两份匹配档案，多匹配返回 409，回滚新增家属 |

| C08 | P2 | 生日前年龄多算一岁；读取沿用过期缓存；未来生日可写入，非法日期返回 500 | 新建与编辑严格解析完整日期并拒绝未来日期；列表和详情按出生日期计算当前周岁，缺生日保留遗留年龄 |
| C09 | P1 | 远期设备时间占据最新步数/位置，正常设备恢复后仍无法替换 | 拒绝超前服务器墙钟 5 分钟以上的旧协议上报，保留缺省时间、离线补报和非 UTC 服务器行为 |

| C11 | P2 | 不足 1 微秒的查询边界被截断，瞬时统计可能漏采样或把起点前采样算入 | 微秒索引向外选候选，再按原始采样时间精确过滤，保持起点包含、终点不含及缓存语义 |
| C12 | P1 | `steps/interval` 日统计被校验层构造的零时长验证记录拒绝，始终返回 400 | 为区间语义构造正时长验证记录，保留其他指标语义校验 |

| C17 | P1 | 邀请码非法天数被静默当成长期有效，使预期有限期的码不失效 | 仅留空、null 或 0 保留长期有效；拒绝负数、小数、非数字和整数溢出，保留正整数原有上限 |

## 验收结果

每批先确认错误行为，再修复。前三批统一运行 **23 个顶层定向用例，全部通过**，包含 9 个非法上报子用例；覆盖上轮五项修复、前三批八项修复、直接相关的围栏事件、原协议解析、热点统计缓存、邀请码竞争和档案绑定约束。原始输出见 [targeted.txt](../../evidence/core-bugs-20261030/targeted.txt)。

第四批运行 6 个直接相关用例并通过，其中新增两个用例；验证默认/离线/超前时间、非 UTC 服务器、旧异常回传不污染最新睡眠状态、正常状态后重新异常计数，以及原协议解析与乱序保护。原始输出见 [reporting-time.txt](../../evidence/core-bugs-20261030/reporting-time.txt)。四批共覆盖 25 个不同顶层用例，非法上报子用例增加到 10 个。

第五批运行 7 个直接相关用例并通过，其中新增普通统计精度、区间日统计两条回归；覆盖写入、候选筛选、精确窗口、缓存、日投影、修订失效和时钟无关的补报夹具。跨午夜的 10 步区间在新日分配 9 步，恰好结束于日界的旧区间不计入，也不造成窗口外重叠冲突。原始输出见 [window-precision.txt](../../evidence/core-bugs-20261030/window-precision.txt)。

PR 早期 CI 的 MySQL 记录确认仅三条新夹具因当天上午的固定时间被 UTC 主机视为未来时间而失败。现已把这些补报日期改为明确的历史日期，不放宽生产时间校验。日统计与围栏接口沿用项目已有的 MySQL 专用夹具，未给遗留 PostgreSQL 构造平台表。

第六批新增两条换绑回归，MySQL 运行 8 条相关路径，PostgreSQL 运行 10 条相关路径，均通过；MySQL 保留数据回滚及重应用用例通过。覆盖三个读取入口、新绑定睡眠告警隔离、A→B→A 同日重绑、缺失字段清空、归档保留和最新日去重。输出见 [daily-ownership.txt](../../evidence/core-bugs-20261030/daily-ownership.txt)。

上一提交 CI 的 MySQL 套件已通过。PostgreSQL 的日上报失败源于 CASE 参数类型无法推断，现改为在 Go 中传入可空观测时间，SQL 直接使用列上下文推断类型；另修正显式主键测试夹具的序列。上述原失败路径已在独立 PostgreSQL 中定向复验通过，不计为新的业务缺陷。

第七批在 MySQL 与 PostgreSQL 各运行 4 条相关用例并通过，新增绑定码、邀请码有效期两条回归。覆盖 11 种非法输入、非法请求不落库、绑定码缺省/空值的一天有效期及实际绑定、邀请码空/null/0 长期有效、合法正天数、邀请码竞争和绑定阈值保留；handlers 的 go vet 通过。本批未增加迁移或前端变更。见 [code-expiry.txt](../../evidence/core-bugs-20261030/code-expiry.txt)。

- 环境：Go 1.26.10、独立 MySQL 8.0.46、独立 PostgreSQL 17.6（服务时区 UTC）、PowerShell 7.6.9。业务数据库用例创建并清理独立随机库。
- `go vet` 仅检查 handlers、health、fence、db 四个受影响包，通过。
- 本次修复包中的前端家属提示与失败反馈已完成一次生产构建；后续批次只修改后端，未重复构建前端。
- 前一轮新增的 MySQL 0017 迁移已实际通过应用、保留数据回滚、重新应用检查。前十三项没有新增迁移；第六批新增 MySQL 0018 / PostgreSQL 0016，仅为日记录补充归属及归档列，不改每日唯一键。
- NULL 设备状态候选被真实非空约束排除，不计入缺陷，也未修改对应指令逻辑。
- PostgreSQL 已完成上述十条关键路径验证；原生安装和真实手表未运行。验证结论对应上述本地关键路径。

## 范围与回退

只修复上述具体行为，保留现有 API、角色模型与设备协议。新建/编辑档案的无效生日现在返回 400，歧义手机号绑定返回 409。旧协议零体征仍可发送，解析结构保持原样。

回退业务代码时保留前一轮新增的观测时间列及索引，不删除健康、位置、家属或照护历史。重新部署前统一升级写入端，避免旧上报实现绕过时间顺序保护。

日记录升级在统一停止旧写入端时执行：现有主表记录冻结升级时可见的当前绑定，不推断更早的历史拥有者；旧归档及未绑定记录没有可证明归属时保持未知，不对新家属展示。未知主表记录标记为旧数据，重新应用迁移不会因后续绑定而补归属。新上报均保存明确归属，覆盖前完整归档。回退只撤销迁移登记，保留新增列、归属及归档数据。升级前混合记录无法凭现有字段追溯拆分。
