# SOS 回执重试与岗位边界上线检查（2026-10-22）

## 本次代码改动范围

- 已完成 HMAC-SHA256 签名验证且在五分钟时间窗内的 `delivered` 回执：
  - 首次接受时，事务内把通知从 `sending/sent` 转为 `delivered`，写入一次照护事件。
  - 同一通知已经持久标记为 `delivered` 时，返回 HTTP 200，不重复插入 `care_incident_event`，不改变其他状态。
  - 未尝试、未知的通知 ID 仍返回 409，错误签名仍返回 401，存储失败返回 500；不因为客户端重试而信任未签名内容。
- 全局岗位隔离：
  - `caregiver` / `auditor` 的普通 ADMIN 会话只可进入已单独实施岗位细分的照护接口，以及个人 MFA 操作；其他旧式 ADMIN 接口直接拒绝。
  - `supervisor` 维持原后台访问权限；岗位查询失败返回 503，不放行。
  - **历史 ADMIN 没有岗位记录时继续按 supervisor 处理**。这是兼容迁移缺口，不代表已达成最小权限。首次上线前应清点并分配全部账号。
  - 家属和设备接口走现有隔离或设备鉴权，不通过 ADMIN 岗位门禁授予额外权限。
- 以上改动不需要数据库迁移，不会自动发送消息，也不会修改现有硬件配置。

## 自动化检查

从 `智慧养老手表管理系统/backend` 运行：

```sh
# 只能使用专用、允许初始化和销毁的测试数据库
export TEST_MYSQL_DSN='root:<测试专用密码>@tcp(127.0.0.1:3306)/suining_test'
export TEST_DATABASE_URL='postgres://careold:<测试专用密码>@127.0.0.1:5432/careold_test?sslmode=disable'
go test -race -count=1 -timeout 600s ./...
go build ./...
go vet ./...
```

重点检查 `TestCareReceiptRequiresTrustedGatewaySignature`、`TestCareImmediateSignedReceiptDuringSending`、`TestAdminDutyGateRestrictsLegacyRoutes` 和 `TestRestrictedAdminRouteAllowlist`。CI 有独立 MySQL 与 PG 服务。如果没有有效测试数据库变量，集成测试可能跳过，不能算通过。

## 真实网关与人员验收（未由本次补丁代替）

1. 发送设备 SOS，确认响应只代表业务入库，通知队列从 pending 到发送中。检查网关接收记录对应相同的 `Idempotency-Key`。
2. 网关接受 HTTP 请求时应仅记录 `sent`；只有正确签名的 `delivered` 回执才能变为送达。连续重复提交同一份回执应持续得到 200，且只产生一次事件。
3. 模拟网关超时、429/5xx、断网、重启与并发派发，验证重试上限、业务主库可恢复性与升级渠道；不要用成功发送替代设备端送达证明。
4. 用护理员、审计员、主管、家属账号逐一核对路由权限；尤其检查前端是否仍呈现无权限的旧管理菜单。客户端隐藏菜单不等于服务端鉴权。
5. 验证超时告警由不同人员接单、处置、独立复核；至少一次演练服务与主库不可用时如何进行线下紧急救助。
6. 仅在真实手表、通知供应商和轮班机构演练通过后，才能把系统描述为满足该场景的可运营服务。未经过医疗或应急认证，不得宣传为自动救援保障。

## 性能、双数据库与值守待验项

- `preview` 现有压测报告的 20 分钟写入 p99 为 14.841 秒，数据对应合并前修复版；本次不声称改善这一指标。需在**当前精确提交**上复跑同环境测试，并测查询、写入、SOS 投递分别的 p95/p99、吞吐与资源占用。
- 只以 MySQL 作为业务权威数据源。PG 离线不应阻断业务，但需要监控分析 outbox 排队、PG 恢复后的追赶时长与重建流程。PG 不是 MySQL 的热备。
- 长期值守使用独立常驻 Go 服务、可信通知网关与人工升级流程；关闭桌面窗口不应是唯一接收设备消息的失效点。
- 生产交付仍需独立完成远程 TLS、备份恢复演练、最小权限账户盘点、告警外部通知、真实硬件及跨 Windows 版本安装检查。

## 回滚

如出现不可接受的旧菜单权限变化，先暂停发布，用 GitHub Revert 撤回引入 `EnforceAdminDuty` 的提交并重新跑鉴权测试。回执幂等修复可独立回滚；回滚后供应商可能再次收到 409，应提前协调重试策略。无 schema 迁移，本次不涉及删除业务记录。
