# 备份与灾难恢复 · MySQL 主库 / 可选 PostgreSQL 分析

适用于当前 `preview` 的 Go + MySQL / PostgreSQL 双库架构，取代早期将 PG 视为业务主库的 2.0.2 说明。**MySQL 及上传图片是业务恢复的必要来源；PG 是可重建的分析投影，不能拿它代替 MySQL 备份。**

## 需要保护的资产

| 资产 | 重要程度 | 备份与恢复要求 |
| --- | --- | --- |
| MySQL 业务库 | 必需 | 事务一致快照、迁移版本、照护任务、队列和审计记录一起保留 |
| 本地/挂载 images 目录 | 必需 | 备份对象和数据库引用需处于协调的写入窗口 |
| `DATA_ENCRYPTION_KEY` 及密钥文件 | 必需 | 独立加密托管；丢失会导致加密字段或会话无法解密 |
| 通知/签收网关配置与凭据 | 必需 | 密钥管理系统保管，不进入日志、文档或公开归档 |
| PostgreSQL 分析投影 | 可重建 | 可以单独备份以缩短恢复时间，但不能用作业务主库备份 |
| Prometheus 历史指标 | 可选 | 保留故障时序的诊断价值，不能还原原始业务记录 |

## MySQL 一致性备份

- 由 DBA 设定和定期验证备份策略：合规的数据保留期、RPO、RTO、加密存储、异地副本、备份失败告警和删除策略。
- 使用 **InnoDB 事务一致快照**（例如 `mysqldump --single-transaction`，或经过演练的在线备份/存储快照）；若需精确到秒的灾备恢复，同时规划 MySQL binlog 保存和重放。
- 结构、触发器、例程及事件是否纳入备份，必须与真实生产库配置一致；恢复时数据库版本、字符集、SQL 模式、时区、迁移校验和及账号权限都要核对。
- 如同时需要图片与引用的一致性，先通过应用侧维护/停写窗口协调快照；单独复制 images 目录并不保证跨数据库与文件系统的原子性。
- 备份输出含姓名、电话、位置和健康数据，必须加密且限制访问。不要把完整 SQL 备份、凭据、日志上传到公开 GitHub。

**只读备份示意**（在已经配置安全凭据的受控环境中，目标路径必须是受限的备份介质）：

```sh
mysqldump --single-transaction --quick --routines --triggers --events \
  --set-gtid-purged=OFF --databases suining > /secure-backup/suining.sql
```

该命令不是完整 HA 或 PITR 方案。根据数据库锁、binlog、MySQL 版本、数据规模以及是否混用非事务表确认一致性；勿把示例直接用于未知生产环境。

## 隔离恢复演练：先核对，再切换

1. 保留原始备份，校验 SHA-256、备份时间、加密与访问控制记录。**先恢复到隔离 MySQL 测试实例，绝不覆盖当前唯一生产副本。**
2. 迁入与备份对应版本的完整 schema、触发器和数据，检查 `schema_migrations` 及照护事件/通知队列的记录数、外键、索引。
3. 同步恢复对应的 images 备份与长期加密密钥。按最小权限建立测试账号；不应将短信/电话网关接到真实用户，避免恢复任务触发真实通知。
4. 验证机构用户登录、老人/设备归属、近一个月健康与告警记录、未处置 SOS、待发送/已送达 outbox、审计记录、图片完整性。
5. 为避免同一 SOS 被再次联系真实人员，必须在确定恢复点、停用旧写入者、核对 `requestId` 及网关幂等策略后，才准许新主库恢复实时发送。
6. PostgreSQL 损坏时，先核对 MySQL 主库正常，再按 `docs/DUAL_DATABASES.md` 以全新分析库和 `analytics-backfill --apply` 重建；旧 PG 是历史分析，不是授权数据源。
7. 演练结束记录实际 RPO/RTO、缺失记录、队列追赶时间、告警到人工响应的时延和回滚步骤，由负责人复核。

## 值守故障时的界限

- MySQL 停机时 API 应拒绝写入，不允许把缓存数据或 PG 分析投影冒充正式业务成功。
- PostgreSQL 离线时记录仍应进入 MySQL outbox；持续积压会消耗主库容量，需监控磁盘与补偿恢复进度。
- Prometheus 告警**不等于已发送寻呼**，只有配置了独立 Alertmanager/值班渠道并实测送达及应答才能形成外部响应闭环。
- 单机 systemd/Compose 重启不能等同跨机器高可用。数据库故障、供电网络故障及真实手表/短信供应商中断仍必须有人工备用救援流程。

旧 Java/H2 数据、旧 PG 主库和当前 MySQL 迁移路径不同，历史数据库转换需要明确、经过实际核对的独立迁移操作。应用回滚不会自动回滚数据库结构，也不能抹除迁移后新写入的业务记录。
