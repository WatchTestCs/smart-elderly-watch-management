# 错误演示：第一版“20 分钟” MySQL 压测（非有效性能基准）

> **这是特意保留的错误演示，用于帮助维护者认识并避免同类错误；不是一次通过的 20 分钟测试，也不是当前后端的性能证明。**
>
> “20 分钟”是**原计划时长**，不是已核实的实际完成时长。对于无法核对的部分，宁可保留空缺，也不能伪造或补算。

## 1. 测试来源、时间与证据级别

这份记录对应 2026-10-20—21 期间第一次计划运行 **20 分钟**的 Go 后端 MySQL／HTTP 健康数据高负载试验。它与后来新增的 GitHub Actions [20 分钟真实 MySQL 隔离复测](https://github.com/WatchTestCs/smart-elderly-watch-management/actions/runs/39622692722) 是**不同运行**。

下表**只是用户保留的旧会话截图所反映的部分进度**。原始请求 JSON、数据库落库快照、带运行 ID 的逐分钟时间序列及当时所有错误堆栈均未在目前提交的源码与报告中找到，因此不能称为原始压测结果或精确测量。

| 项目 | 可见的历史信息 | 证据级别 |
|---|---|---|
| 预定测试时长 | 20 分钟（1,200 秒） | 测试目标，不等于实际完成 |

## 2. 为什么要公开这个错误演示

这里展示的是**验证方法和数据解释方式的缺陷**，不是把一次失败当作软件性能成绩。

1. **计划运行 20 分钟，却把未完成的时间段描述为“完整 20 分钟”**。第 16 分钟附近出现错误，整轮应记为“失败／中止／无法核验”，绝不能把已成功处理的部分外推为 1,200 秒的稳定吞吐。
2. **混淆 HTTP 成功和持久化成功**。即使有 200/业务 ACK，也必须再核对 `health_sample` 与 `health_change`、去重和版本历史。当前没有同一轮的核对数据。
3. **缺少错误分层证据**。500 是服务端错误，503 可能来自健康探测、数据库连接争用或服务状态切换；不能仅凭返回码直接给特定 SQL、索引或业务逻辑定罪。
4. **中途失败可能丢失完整压测结果**。仓库现有 [cluster-loadtest.py](../../../scripts/cluster-loadtest.py) 的汇总 JSON 主要在全部工作者结束后才写出；若进程被中止或某个工作者没有返回，可能拿不到终态汇总。该脚本可用来说明记录设计的风险，但**目前无法证明它就是第一版历史运行所使用的精确脚本和参数**。
5. **在事务锁内做大量读取会放大延迟**。旧规则设备事务持有 `SELECT ... FOR UPDATE` 锁后做最近值／基线／活动查询；旧业务池还供周期性探测使用。这是源码可审计的风险组合，但不等于本轮具体 500/503 的单一、已证实原因。

## 3. 避免重犯：最小验收标准

- **结果不可覆盖：**每分钟写出可恢复检查点，始终携带运行 ID、实际起止时间、尝试与完成请求数、HTTP 200/500/503、超时和未知结果数量；即使异常退出也保留目前已有的原始证据。
- **业务与数据库双重核对：**HTTP ACK 数与唯一记录落库数、变更历史和去重状态必须有相同运行 ID 可追溯；不对超时的不确定写入直接自动重试。
- **把错误归因建立在证据上：**保存数据库连接池 InUse/WaitCount/WaitDuration、对应慢 SQL、执行计划、锁等待、应用错误和健康探测状态。指标与时间轴需能关联。
- **报告必须区分**目标时长、实际覆盖时长、是否完整、是否有丢失数据、是否可以与其他轮次比较。测试中止或原始日志缺失即明确标记为 **INVALID / NOT VERIFIED**，绝不以推算填补。
- **复测用隔离数据：**新工作流采用 Go 1.23.2、独立 MySQL 8.4、合成样本和检查点。它也只有在日志、JSON、持久化校验实际完成后，才有资格报告完整通过。

## 4. 不应得出的结论

**不得从本例声称**：
- 原版在 20 分钟内完成了约 8,322 批或达到任何精确的平均 QPS。
- 第 14–16 分钟以外的吞吐／p99／错误数。
- 某一特定索引已彻底解决 500，或者健康探测修复已彻底解决所有 503。
- 将另一轮短时性能数据拼接到这次未完成的 20 分钟中。
- 本轮代表当前 `preview` 代码、真实设备、生产 MySQL 或 SOS 通知投递的长期稳定性。

**保留这份反例的目的，是避免未来维护者复制错误的测试方法或错误解读，不是包装失败结果。**
