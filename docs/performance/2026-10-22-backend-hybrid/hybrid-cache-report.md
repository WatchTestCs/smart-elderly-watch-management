# 健康统计冷热混合架构：实现与验证

2026-10-22，本地 preview 工作副本已增加有界的健康统计结果缓存。完整采样和修订事件继续由 MySQL 先事务提交、再确认写入；PG 分析投影保持原有异步持久化流程。高频重复查询复用内存中的统计结果，缓存未命中时读取磁盘数据库中的历史。没有新增 Redis、表或数据库迁移，也没有修改告警基线随时间推进的计算。

## 缓存边界与一致性

- `HEALTH_HOT_CACHE_MIB` 默认 16，0 禁用，允许 0–256；无效值回退 16。配置通过应用环境继承，Compose 也已接入。
- LRU 最多 2,048 项、单项最多 64 KiB，入缓存后 30 秒过期。按结果 JSON 长度加每项 256 字节开销计费，键为固定长度 SHA-256。预算含估计元数据，不是整个进程堆或 RSS 的硬限制。
- 老人、来源、来源设备、指标、语义、带偏移和完整精度的起止时间均参与键计算。键编码失败绕过缓存，结果编码失败不入缓存。
- 每次命中前重新鉴权并读取数据库已提交修订号。任何实例通过现有样本写入协议进行新增、更正、删除，都会使旧缓存无法命中。未命中时前后两次修订号不同，不缓存本次计算。
- 缓存校验失败回到原查询路径，数据库断开时不会凭旧缓存返回成功。重启后按数据库状态重建缓存。
- 冷热划分按访问热度及 LRU 管理；完整历史仍在现有数据库磁盘卷中。数据库自身的缓冲池仍会缓存高频磁盘页，没有将全库搬入内存，也不删除历史数据。

## 实测读取性能

AMD Ryzen AI 9 H 365，Windows amd64，Go 1.27.2，GOMAXPROCS=4、GOMEMLIMIT=512MiB；真实 MySQL 8.0.46，512 MiB buffer pool，刷盘持久性保持开启。单独创建临时测试库，实际通过 `health.SaveBatch` 持久化 10,000 条心率采样，再对相同统计请求进行三组每组约 3 秒的顺序测量。

| 指标（三组算术均值） | 直接读数据库 | 内存命中 |
|---|---:|---:|
| 每次处理耗时 | 23.252 毫秒 | 0.089078 毫秒 |
| 每次分配字节 | 29,940,968 | 9,838 |
| 每次分配次数 | 70,401.7 | 80.0 |

该条件下处理耗时比约 **261.0 倍**，分配字节减少约 **99.967%**。缓存命中仍有一次数据库修订号检查。三次原始读库耗时为 23.348, 23.389, 23.020 毫秒，命中为 0.089087, 0.088912, 0.089236 毫秒。

这是完整统计处理函数的进程内请求基准，包含 JSON 读写、管理会话上下文、权限分支和真实数据库查询，使用 httptest，不含真实 HTTP 网络、生产中间件或家属授权查询的额外开销。测试名中的 disk 指禁用应用缓存的数据库路径；MySQL 缓冲池经过预热，不是物理冷盘性能。分配字节是每次请求累计分配，不是常驻内存或峰值。

数字只适用于同一修订号下、相同时间范围的重复统计。不断上传、更正或变动查询范围会降低命中率，未命中额外读取两次修订号；本次没有测出持续写入场景的净收益。复用既有统计结果不等于重新处理 10,000 条采样，不能换算成“样本预处理/秒”或上传吞吐。本次没有重新执行此前的 20 分钟极限压测，不更新此前的落库容量结论。
