# 503 / 500 修复与双库复测报告

本地最终修复版（2026-10-22）完成 1200 秒压力准入及在途排空。上报成功 **9,484 批**，服务端 POST 状态分布 **{'200': 9484}**，客户端上报错误 **0**。独立 SQL 核对采样及变更事件各新增 **1,896,800** 条，与成功响应一致。本结论限于本次隔离负载，不代表任意过载或实际断库时不会返回错误。

## 根因与修复

1. **503：探测与业务共用连接池。** 20 个业务连接占满时，5 秒 Ping 等不到连接，后台撤下整个业务 API。真实 MySQL 回归将池缩为 1 并持有事务，原版连续两次失败（context deadline exceeded），修复版通过。独立探测池最多 1 个连接，保留真实断线检测和恢复，业务池仍为 20。
2. **500：设备锁等待超过驱动 15 秒读取时限。** 180 秒诊断负载实际捕获 lock_device 阶段 invalid connection，驱动同时记录 i/o timeout。InnoDB 锁图显示规则事务执行历史基线聚合时持有设备行，离线整表 UPDATE 在等待时进一步锁住其他设备。离线扫描改为每页 100 行，FOR UPDATE SKIP LOCKED，跳过的设备下一轮检查，保持事务与一次离线事件语义。
3. **缩短规则持锁时间。** 新增 0008 来源前缀索引，查询加入可用索引的完整来源等值条件，继续保留完整 BINARY 核对。相同空基线查询原计划读取 49,800 行、约 4.26 秒，新计划定位空范围、约 0.019 毫秒（EXPLAIN ANALYZE 单次执行；冷热缓存不同，不能据此换算整体倍数）。大小写和 64 字符前缀碰撞均做真实 MySQL 回归。

第一轮仅采用来源前缀索引，20 分钟后段仍产生 100 次 500，原始结果保存在 fixed20/，不计作修复成功。第二轮新增 0009 虚拟列及覆盖索引，对常见设备标识直接在索引中完成数值聚合，保留完整 BINARY 来源核对；长标识继续使用原路径。真实 MySQL 回归验证了非空聚合的数值，并断言执行计划 using_index=true。本轮复用第一轮的同一来源、使用新 recordId，让已有非空历史基线从第一秒参与计算，避免空窗口掩盖问题。

没有把未知错误改成成功，没有自动重放失败业务写入，没有增加业务连接池、放宽 SQL 超时或降低刷盘持久性。针对已确认过载链路修复，真正断库仍返回 503，未预期 SQL 故障仍可能返回 500。
