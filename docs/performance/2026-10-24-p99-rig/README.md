# p99 尾延迟试验台与因子量化（2026-10-24）

目标：最大化降低 p99。先建可复现试验台（`internal/handlers/p99_rig_test.go`，
opt-in `P99_RIG=1`），再量化各因子，避免凭单轮信号调参。所有臂为真实
MySQL 8.4（Docker loopback）、同设备（WATCH001）闭环写入、批 200。

## 试验台

闭环 worker 全部写同一设备（owner 时钟串行点=文档点名的 p99 来源），
可开后台规则引擎 tick（5s 间隔，与浸泡一致），GOGC 可外部注入，
输出 JSON（p50/p95/p99/p999/max、GC 周期、请求数）。

## 因子量化结果（60s 臂 × 8 worker，交错重复）

**1. GOGC：GC 周期 4× 削减是真的，p99 无可复现改善。**
default vs 300 三轮交错（中位）：p99 1403 vs 1414 ns 级持平；
GC 周期 481→122 确定性下降；solo（1 worker）复核同样持平
（默认 ~162 vs 300 的 158 ms），且 300 的 p50 略差（35.2 vs 31.9）。
**结论：堆仅 ~3MB、GC 助耕暂停远小于 DB 往返，调 GOGC 不动 p99——
runtuning 默认保持 200，不改。**

**2. 后台规则 tick：单轮测得 +14% p99，未复验，结构上不动。**
规则评估是产品功能；移出进程/独立池涉及故障恢复设计（文档既有判断）。

**3. 本日全部 CPU 优化对 p99 的真实贡献：服务时间层显著，饱和层被排队吞没。**

| 口径（1 worker=纯服务时间） | 基线 ac1fceb | 当前 | 变化 |
| --- | ---: | ---: | --- |
| p50 | 35.6ms | 31.9ms | **-10%** |
| p95 | 102ms | 84ms | **-18%** |
| p99 | ~207ms | ~162ms | **-22%** |
| max | ~394ms | ~243ms | **-38%** |

| 口径（8 worker 同 owner 饱和） | 基线中位 | 当前中位 | 变化 |
| --- | ---: | ---: | --- |
| p50 | 305ms | 293ms | -4% |
| p99 | ~1374ms | ~1403ms | 噪声内持平 |

**机制**：同 owner 饱和时 p99 ≈ 排队深度(~7) × 服务时间 + MySQL 争用。
本日 CPU 工作把单批服务时间省下 ~4ms（35.6→31.9），×7 ≈ 28ms ≈ 2% p99
——低于共享宿主噪声，故饱和层测不出；但 solo 层的 -22% 是服务时间
本身的真改善，对低并发真实设备流量直接生效。

## 对"最大化降 p99"的结构性结论

1. **饱和同 owner 场景的 p99 由 owner 时钟串行化 × 单批 DB 服务时间决定**，
   不由 CPU/GC 决定。降它的合法杠杆只剩"削减单批 SQL 往返/语句成本"，
   而批语句已充分批量化（下一门槛是仓库自列的 EXPLAIN ANALYZE 定位
   三条大语句的耗时占比，需要独立数据量级实验）。
2. owner 时钟串行化是正确性语义（修订号顺序），不可并行化。
3. 真实低并发流量（设备每 5s 一批、无排队）的 p99 直接享受 -22% 服务时间。

