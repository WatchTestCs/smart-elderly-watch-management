# 把输入准备移出数据库事务（2026-10-23）

基线 `60be581e69048c6e9f3be680fcbee3067b8750e8`；[此前全部实验与回退](previous-pr30.md)原样保留。上一轮不能稳定改善小请求 p99，本轮削减事务与设备锁内不必存在的 CPU/内存工作。

## 实现

多条健康上报保留原先的逐条来源检查和规范化，再进行一次无锁的主库设备认证读取。认证失败立即返回，不开启写事务，也不做整批 JSON 编码。认证成功后通过 health.PrepareBatch 完成原有的第二次规范化及输入 JSON 编码，然后才开始写事务。

输入准备不保存 owner、device identity digest 或 revision。默认路径仍按原先的主键 SELECT FOR UPDATE 锁设备，重新核对密钥、设备号、停用状态、owner 与 binding epoch，再传入最新归属保存。实验 owner-first 模式仍在提交前做完整设备绑定复核；没有把它改为默认模式，也不改变跨副本锁顺序要求。

SavePreparedBatch 在现有事务内计算身份、锁 owner、比较版本/冲突并写入、提交由调用者执行。数据未落库前仍不确认成功。同版本的旧 JSON 规范化比较仍在锁内；本轮只移动输入准备。旧 SaveBatch API 直接共享规范化与存储函数，不创建单次消费对象或执行原子消费，因此其他调用者保留直接路径。单条 HTTP 请求也保留原先的先开始事务、事务内认证及 SaveBatch 流程；批量路径才使用事务外准备。

PreparedBatch 是不透明的单次消费对象：原子标记只允许一个保存尝试，失败也不能复用，禁止复制或跨请求池化。规范化的字段和编码的 payload 由本次请求持有；metadata 编码后不再从调用者 map 读取，也不在准备对象中保留 map。HTTP 处理器在准备完后释放解码切片与 metadata 引用，减少等待数据库/commit 时的堆驻留。批量准备的代价包括一个额外的小对象与单次原子操作；普通 SaveBatch 不承担这部分成本。

## 验证与边界

单元测试验证规范化快照、调用者修改不影响 payload、32 个并发消费者只有一个成功、非法/零/已消费对象拒绝。真实 MySQL 验证当前 owner 赋值、原始 JSON 快照落库、跨 owner 再消费失败且不增加历史。原有并发解绑、密钥轮换、停用、owner-clock 争用与失败回滚用例继续运行。

A/B 保留相同五种 HTTP 配置与事务控制组，夹具原样复制到 60be581：1/200 条×1/4 客户端各三轮×500 请求，另有每样本 1024 字节 metadata 的 200 条×4 客户端各三轮×200 请求。测量仍包含完整请求/响应和真实持久化确认，所有轮次校验响应与落库数。事务组继续记录 begin/save/commit 及最慢事务，不能只用输入准备耗时当作总延迟。

封闭客户端、loopback HTTP 和 CI runner 不代表生产 SLA。大输入提前准备可能增加同时编码时的 CPU 竞争；小请求可能受额外对象/原子检查影响，最终收益以全部场景对照为准。新增单连接池回归，验证单条与多条路径都不在持有事务连接时再借用认证连接，防止池饥饿。真实 DB 用例本地跳过，精确提交的 CI 和全部原始结果见 [PR #30](https://github.com/WatchTestCs/smart-elderly-watch-management/pull/30)。

## 首次实测与收窄

505094f 的首轮 A/B 在普通 200 条、4 并发 HTTP 中得到 p99 -30.5%，但单条、4 并发 p99 +80.8%，大 JSON GC 次数 +75.4%；不能把批量收益推广到单条。后续收窄为单条恢复旧事务流程，普通 SaveBatch 也不再创建准备对象/原子消费，再重新跑完整对照。首轮全部结果保留在 PR 描述；未归因为外部噪声。

认证读与批量写事务是两次顺序借用连接，idle=0 或其他池预算可能增加建连/排队成本；本轮性能矩阵使用默认池设置，单连接测试只证明没有嵌套借用死锁，不证明该配置的性能。
