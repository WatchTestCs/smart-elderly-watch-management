# 会话微缓存（opt-in）：认证链路 116×（2026-10-24）

前置事实：本日优化后，已登录请求端到端 0.54ms 中 **~0.46ms（85%）是那一次
会话读库往返**（p99-rig 与链路基准共同确认，HTTP/中间件部分已压到 ~80µs）。
代码层再往下只剩一个杠杆：让会话读取不每请求过库。

## 设计（显式的安全-性能取舍，opt-in 默认关闭）

`SESSION_CACHE_MS`（0=关闭默认；开启须 250..5000，config.Validate 校验）：
- **命中**：TTL 内同会话跳过读库，直接返回缓存条目（payload+principal 已含
  写入时的 MFA generation 校验结果）。
- **同副本撤销立即生效**：`Destroy`（登出）与 `Revoke`（改密吊销，按 role+id
  清全部条目）同步失效缓存——占撤销场景的绝大多数。
- **跨副本撤销有界延迟**：他副本删除 web_session 行后，本副本最多再服务
  ≤SESSION_CACHE_MS（默认建议 1000ms）。这是有界、可配置、文档化的取舍。
- **内存上界**：活跃会话 × TTL 内并发，条目惰性过期（~1KB/条）。
- 生成号（factor generation）校验在条目写入时已生效；TTL 内不重查。
- 默认关闭时**逐字节保持**"每请求实时读库、撤销立即"的原语义。

## 验证

- 新增 4 个行为测试（真实 MySQL）：TTL 内命中/过期回落、同副本 Destroy
  立即失效、Revoke 按身份精确失效（他人会话存活）、默认关闭时逐请求实时读库。
- `go build/vet ./...` + MySQL 8.4 + PostgreSQL 16 全量回归通过（session
  包含既有撤销/共享/generation 吊销用例全部不弱化）。

## 边界与运维指引

- 默认关闭=零语义变化；开启是部署方对"跨副本撤销 ≤TTL 延迟"的显式接受。
  单副本部署（桌面端/单机 compose）无跨副本问题，可放心开启。
- TTL 内修改密码的他副本吊销窗口 ≤TTL——对高安全要求保持 0。
- 登出/改密的同副本场景不受影响（立即失效）。
