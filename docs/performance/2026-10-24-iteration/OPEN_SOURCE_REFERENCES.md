# Open-source performance references — 2026-10-24

## Request-scoped authentication

[SCS LoadAndSave](https://github.com/alexedwards/scs/blob/master/session.go) loads an authoritative session once and carries it in the request context. [Gorilla Sessions Registry](https://github.com/gorilla/sessions/blob/main/sessions.go) similarly stores loaded sessions in a request-local registry. This patch adapts the request-local idea with a private Store-scoped key, matching cookie and expiry checks. It does not trust the existing principal-only WithContext function as authentication proof, add a process TTL, or cache across network requests. Session payload and enabled-factor generation are retrieved by one indexed LEFT JOIN and checked against the encrypted identity. Fresh requests and explicit Get calls remain authoritative after revocation. These are locally written adaptations of the pattern, with no imported session dependency or copied upstream source. Both projects publish BSD-style licenses in their repository LICENSE files.

## Pagination

Sources were read before changing the list handlers. This note compares mechanisms; it does not claim local performance results.

| Primary source | Observed implementation or documented behavior | Fit here |
| --- | --- | --- |
| [Spring Data Commons 4.0.0 `PageableExecutionUtils`](https://github.com/spring-projects/spring-data-commons/blob/4.0.0/src/main/java/org/springframework/data/support/PageableExecutionUtils.java) | Data first; infer totals for a partial first page or a nonempty partial later page; otherwise invoke the count supplier. [Apache-2.0 license](https://github.com/spring-projects/spring-data-commons/blob/4.0.0/LICENSE.txt). | Useful empty-page boundary: an empty later page does not establish total zero. Full pages still require a count. |
| [Django 5.2 `Paginator`](https://github.com/django/django/blob/5.2/django/core/paginator.py) | Cache count per paginator instance, validate the requested number, then slice the object list. [BSD-3-Clause license](https://github.com/django/django/blob/5.2/LICENSE). | Separate count and bounded page are a mature baseline. Its out-of-range exception differs from this API's empty-array plus exact-total contract. |
| [MySQL 8.4 window optimization](https://dev.mysql.com/doc/refman/8.4/en/window-function-optimization.html) | A derived query containing window functions cannot merge into the outer query and is materialized. | `COUNT(*) OVER()` can force broad row processing; one SQL command alone does not prove a win. |
| [MySQL 8.4 derived-table optimization](https://dev.mysql.com/doc/refman/8.4/en/derived-table-optimization.html) | `LIMIT` and aggregation prevent merging; materialization may be delayed. Derived ordering is not generally propagated through joins. | A bounded page plus one-row aggregate can preserve separate count/page plans. Explicit outer ordering is required. |
| [MySQL 8.4 LIMIT optimization](https://dev.mysql.com/doc/refman/8.4/en/limit-optimization.html), [PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/18/queries-limit.html) | LIMIT can reduce row work; deterministic ordering matters; large offsets still consume work. | Preserve existing unique orders, filters and page-number API; do not introduce cursor pagination in this patch. |

Iteration 1 cross joined the existing bounded page with an independent scalar count, then restored the original ordering outside the join. Populated pages needed one database command. Empty later pages needed a count-only fallback. Central matched A/B/B/A measurements retained regressions: 10,000-row family selective reads about 76% slower, customer out-of-range about 27% slower, and text out-of-range about 7% slower. See the retained [rejected pagination runs](evidence/rejected-pagination.txt); these are synthetic measurements, not production claims.

Iteration 2 uses count LEFT JOIN bounded page for customer/text. One aggregate row survives even when the bounded page is empty; the non-null primary key is scanned into a pointer and its NULL sentinel omitted from the JSON array. This preserves an exact total in one command without a fallback duplicate count. Both inner page selection and outer output retain the original ordering. The only projected rows materialized for the page remain bounded by LIMIT.

Family iteration 2 retains the original direct bounded SELECT and applies the Spring-style partial-page inference: a nonempty partial page establishes offset plus length; an empty first page establishes zero; full pages and empty later pages still execute the independent exact count after closing rows. This removes the new derived join from the selective family query plan. The final MySQL/PostgreSQL contract checks and matched timing passed; measured minor regressions remain listed in README.md.

No upstream source code or dependency is copied. References inform the locally written SQL and the empty-page contract. Benchmark page 1, selective filters, last partial pages and out-of-range pages at small and larger cardinalities; discard candidates with material regressions rather than generalize synthetic results to production.

## Calendar decoding reference

[Go 1.23.2 `time.Time.Date` and `Clock`](https://github.com/golang/go/blob/go1.23.2/src/time/time.go) expose the existing location-aware calendar and clock decomposition. The statistics/activity candidate reuses those standard decoded values within the request instead of creating formatted date strings or repeatedly decoding the same time. It preserves sorting and arithmetic, and recomputes when the actual `Location` pointer changes, including implicit-zone/DST cases. The reference is Go's standard-library implementation under its [BSD-style license](https://github.com/golang/go/blob/go1.23.2/LICENSE); no external dependency or upstream code is imported. The differential checks, targeted race tests and matched timing passed; final results and remaining regressions are recorded in [README.md](README.md).

## Other database mechanisms considered

[pgx v5.7.5](https://github.com/jackc/pgx/tree/v5.7.5) supplies batching, prepared statements and binary transfer; [go-sql-driver/mysql v1.9.3](https://github.com/go-sql-driver/mysql/tree/v1.9.3) supplies safe interpolation fallback. Existing application batching/statement reuse already uses these techniques. Replacing them merely to add another cache would not establish an improvement. [RocksDB](https://github.com/facebook/rocksdb/wiki/RocksDB-Overview) and [MyRocks](https://github.com/facebook/mysql-5.6/wiki/Getting-Started-with-MyRocks) are storage-engine designs with compaction/deployment tradeoffs; they are not drop-in replacements for these Go query paths. No engine migration is adopted without a matched workload and data-contract migration proof. The selected external decoder and the rejected Sonic candidate are recorded separately in [JSON_DECODING.md](JSON_DECODING.md).
