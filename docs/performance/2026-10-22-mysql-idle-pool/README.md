# MySQL 连接池空闲连接与突发负载 A/B（2026-10-22）

## 改动与结论

主库应用池继续保留 **最多 20 个活跃连接** 和独立的 1 个健康探测连接；将默认空闲连接上限由 **5 → 20**，以减少突发负载之间的 MySQL 握手、连接建立与池等待。没有改变事务隔离级别、写入/通知流程、触发器、索引或持久化设置。

允许通过环境变量 `MYSQL_MAX_IDLE_CONNS` 设置 **0–20** 的整数；未设置默认 20。为避免无意造成连接配置异常，非法取值使主库初始化明确失败，而不是默默使用意外默认值。

## 两次独立真实 MySQL 8.4 A/B

每次使用同一临时数据库与 `go-sql-driver/mysql` 原 prepared-statement 参数语义，按 **5→20→10→10→20→5** 交叉顺序测试。每个 trial 从零空闲连接开始，使用 32 个并发请求进行一次不计入延迟结果的预热，再运行 8 轮 32 并发 `SELECT revision FROM health_clock WHERE id=?`，轮次之间间隔 100 ms。每轮共采样 256 次查询；每个配置在两次独立 CI 运行合计 4 个 trial。连接池上限始终为 20。

| 空闲上限 | 后续突发查询 p50 平均 | p95 平均 | p99 平均 | 每 trial 额外空闲连接关闭数 | 每 trial 池等待时间 |
|---:|---:|---:|---:|---:|---:|
| **5（基线）** | 5.703 ms | 7.761 ms | 8.134 ms | 135 | 434.2 ms |
| **10** | 4.082 ms | 6.450 ms | 7.384 ms | 90 | 293.5 ms |
| **20（新默认）** | **2.470 ms** | **3.568 ms** | **3.913 ms** | **0** | **215.6 ms** |

在**这组突发参数化查询**中，连接池空闲上限 20 相比 5 的 p99 约降低 **51.9%**，即 p99 延迟约为原先的 1/2.08。它不是 HTTP 端到端事务 p99、写入持续吞吐或 SOS 送达 p99 的改善幅度。

## 风险与权衡

1. 最高保留 20 个空闲应用连接，可能增加 MySQL `Threads_connected`、连接缓存和服务器会话内存。每个应用副本总连接容量仍为**应用 20 + 专用健康探测 1 = 21**；多副本、管理员及其他服务应一起纳入 `max_connections` 和内存预算。**不能只从单台 CI runner 得出生产服务器内存充足的结论**。
2. MySQL 客户端仍在 5 分钟生命周期后更换连接，避免无限占用。新默认值仅减少**空闲容量造成的提前关闭**，不是永久连接。
3. A/B 只测参数化轻查询及间歇性请求，没有进行同拓扑健康写入、真正的行锁竞争、持久 redo、磁盘同步、网络波动或压力下持续 20 分钟的完整 HTTP p99 测量。不同数据库规模、拓扑和网络 RTT 可能改变收益。
4. 故障或资源预算不符时，设置 `MYSQL_MAX_IDLE_CONNS=5` 并重启恢复原空闲池行为；这次无数据库迁移，回退不涉及任何表或数据。
5. **否决的另一个候选**：普通 `INSERT` 替换健康样本 `UPSERT`。独立 MySQL 16 并发/4 老人 A/B [39760680709](https://github.com/WatchTestCs/smart-elderly-watch-management/actions/runs/39760680709) 测得：普通 INSERT 两轮平均约 13,794 行/秒，而原 UPSERT 约 14,647 行/秒，未获得稳定 p99 优势。因而没有改动业务存储语句。

## 后续要攻克的真正瓶颈

原 20 分钟历史压测显示约 **14.841 秒 HTTP p99** 和 1,268 次 InnoDB 行锁等待，不能误当成本次 A/B 的基线。下一轮应在**同一负载**记录健康 API 与规则线程持锁时长、`health_owner_clock` 等待、MySQL redo 量、数据库进程内存及池等待指标；对持锁期间的 SQL 读路径做分阶段时序，再决定是否值得重排昂贵的规则/采样读写。

本轮目标是**以受限资源成本优化突发 SQL 查询尾延迟，同时拒绝没有正收益的索引、触发器和 SQL 语句替换**。
