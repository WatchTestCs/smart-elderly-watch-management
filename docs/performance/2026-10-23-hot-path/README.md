# 后端架构与 CPU 热路径优化（2026-10-23）

基线：`preview@3dbd79d62b3961f4791a41195c400c8395651a13`。本次不改数据库归属、事务边界、设备 ACK、通知送达或权限语义。现有 #27、#29 不在本次改动中。

## 架构判断

当前是模块化单体：`cmd/server` 管启动与依赖发布，`handlers` 管 HTTP 和事务编排，`health/rules/care/notify` 管领域处理，`db` 提供双驱动适配；MySQL 保存业务及 outbox，PG 保存可重建的异步分析投影。规则、通知、照护和分析作业在服务进程内启动。独立部署服务并不意味着每个作业已经拥有独立进程或连接池。

| 路径 | 已有可取设计 | 性能约束与判断 |
| --- | --- | --- |
| 健康写入 `health/store.go` | 每批最多 200 条；写前规范化；身份摘要；批量样本与事件写入；owner 时钟保持提交顺序 | owner 时钟、设备归属行锁是串行点；同一 owner 并发不会随 CPU 核数线性扩展。必须测锁等待，不能删除锁破坏游标与归属正确性 |
| SQL 适配 `db/database.go` | 512 项有界 FIFO，仅缓存 SQL 结构，参数仍绑定 | 原代码每次复制参数数组，放大批量写入堆流量；共享 RWMutex 是下一步需 profile 的争用点。本次优化顺序参数绑定，保留缓存容量及锁实现 |
| HTTP 指标 `observability/metrics.go` | 路由归一化、长尾桶、抓取时先快照再写客户端 | 原统计每次执行 15 轮边界格式化、19 项字符串键更新；锁内分配与字符串散列压缩了多核并发。本次改为紧凑数值直方图 |
| 规则 `rules/engine.go` | keyset 分页；最多 8 个设备事务；覆盖索引；紧凑候选和私有证据缓冲 | 设备锁内多条查询及历史聚合可能主导尾延迟；加 worker 可能与摄取竞争 20 条业务连接。需按历史量测 EXPLAIN ANALYZE 和 pool WaitDuration |
| 分析 `analytics/batch.go` | 有界批次；同实体合并；PG UNNEST 一次往返；按事件版本幂等 | PG 写入期间持有已选 MySQL outbox 行锁和事务连接；应先测积压、事务持续时间及网络延迟，再决定租约式消费设计 |
| 会话 `session/session.go` | MySQL 服务端撤销、多实例可见、MFA generation 检查 | 已登录查询含会话读取、解密及 factor 查询；跨网 RTT 可能大于本次 CPU 节省。不能用普通 TTL 缓存牺牲即时撤销 |
| 连接与运行时 | 20 条业务连接、独立 1 条探活连接；opt-in cgroup v2 调参 | 更多连接、GOGC 或 GOMAXPROCS 都有资源代价，不能统一调至最大；探活隔离值得保留 |
| 限流及日志 | IP+路径滑动窗口；结构化逐请求日志 | 限流全局锁和全量清理、日志下游阻塞值得后续独立测量；本轮没有运行数据证明它们是主要瓶颈 |

## 本次实现

1. 编译 SQL 模板时识别 `$1,$2,...` 的顺序映射。命中后直接传递调用方参数的只读、限容量切片，避免重复分配和线性复制。重复、跳号、乱序参数仍复制重排；缺参仍在执行前报错；多余参数仍被丢弃。不在缓存中保留参数值，不跨请求复用健康数据缓冲。
2. 每组 HTTP 标签保存连续的 15 个 `uint64` 非累计桶、总数和 sum，并且只在首次出现时建立不可变指标名称。每次记录只查一次标签映射、更新一个桶；抓取时复制连续的数值快照、重建累计桶并复用不可变名称；预留结果容器容量。保留所有桶（包括零）、`+Inf`、名称、标签和慢抓取隔离。

这些改动通过减少堆对象、指针扫描、字符串散列、内存写入和持锁时间接近硬件的有效工作方式。未引入 unsafe、汇编、线程绑核、无界缓存或运行时参数变化。缓存锁仍存在，不能称为无锁设计。

## 测量方法及边界

Go 1.23.12，Linux amd64，AMD EPYC 9V74；cgroup 配额 8 核、内存 8 GiB；所有报告基准设 `GOMAXPROCS=4`。相同新增基准复制至基线 worktree，分别执行修改前后版本，各 3 轮。共享宿主与按版本先后测量仍有噪声；没有统计显著性或独占物理核保证。另有初轮 5 轮数据仅作开发参考，未纳入本表。

- 参数绑定基准只测热缓存的适配成本，2800 参数模拟 200×14 列的规模，不执行 SQL。
- `ObserveHTTP` 只测统计，标签字符串已在循环外建立；零分配不代表整个 HTTP 请求零分配。
- HTTP 基准使用完整指标中间件、UUID、标签和结构化日志格式化；处理器只返回 204，日志写向 `io.Discard`。没有数据库、实际网络或磁盘日志成本。
- 抓取基准预置 100 组标签，包含格式化与内存响应写入；请求端优化将部分工作迁移到了抓取端，必须同时看该项成本。

三轮中位数；各行均为局部基准，耗时单位 ns/op。

| 基准 | 修改前 ns/op | 修改后 ns/op | 前→后 B/op | 前→后 allocs/op |
| --- | ---: | ---: | ---: | ---: |
| 1 参数绑定 | 31.28 | 34.8 | 16 → 0 | 1 → 0 |
| 14 参数绑定 | 87.98 | 34.39 | 224 → 0 | 1 → 0 |
| 2800 参数绑定 | 14224 | 89.53 | 49152 → 0 | 1 → 0 |
| HTTP 直方图记录 | 4667 | 30.27 | 2672 → 0 | 59 → 0 |
| HTTP 中间件（空处理器） | 8777 | 1411 | 3602 → 1256 | 87 → 28 |
| 100 组标签抓取 | 1.10328e+06 | 845761 | 779720 → 796105 | 5823 → 5824 |

单参数绑定的中位耗时本轮从 31.28 ns 增至 34.8 ns（约 11%）；该路径只确认消除分配，不能声称时间改善。多参数与批量路径的收益更明确。

HTTP 直方图记录从每次 59 次分配降为热路径零分配；完整中间件仍有 28 次分配。2800 参数绑定不再额外分配 49,152 字节。100 组标签抓取的耗时下降，但约增加 16 KiB（约 2.1%）临时内存及 1 次分配，这是连续数值快照的代价。保留不可变指标名称避免每次抓取重建 1900 个字符串。

## 后续性能门槛

先做真实 MySQL+HTTP 混合负载，分别测试同 owner 和不同 owner、规则开启和关闭、PG 正常和高延迟、健康批次 1/50/200、日志真实落盘；记录接收时间起算的 p50/p95/p99、错误/拒绝数和实际到达速率，同时收集 CPU/alloc/mutex/block profile、GC CPU、RSS 与 pool 等待。使用隔离库及合成记录，禁止把生产健康数据写进 profile 附件。

若 SQL 缓存锁在 profile 中显著，再比较分片/不可变快照的散列和缓存失效成本；若数据库 RTT 主导，优先合并语义等价查询和缩短锁内等待；若 GC CPU 主导，再以真实活跃堆验证 GOGC/GOMEMLIMIT。PG 消费租约与 worker 池隔离涉及故障恢复和资源分配，应另立设计并做崩溃重放测试。

这些是需测量的下一步，不是已实现收益。不能将本次纳秒级微基准换算成整体吞吐倍数或设备容量承诺。
