# P0 设备密钥存储变更（依赖 PR #1）

目标：旧版将 `device.secret` 以明文写入本机 H2 数据库；V3 升级在**应用启动、对外服务之前**，把现有设备密钥转换为带域分离的 SHA-256 摘要，创建和重置也只保存摘要。手表仍使用原来的 `deviceNo`、`secret` 字段和旧密钥字面值，无需更改设备客户端通信契约。

## 安全边界

- 设备密钥由服务器 `SecureRandom` 从 32 字符高熵字符表生成；**不得用人类密码使用本算法**。设备密钥如果允许用户自定义低熵值，必须更换为 Argon2id/scrypt 等专用密码哈希。
- SHA-256 摘要以 `sha256$` 前缀识别，长度 50，兼容既有 `device.secret varchar(64)`，无数据表列变更。不把前缀匹配失败的密钥当作有效明文认证。
- 创建与重置 API 仅在有管理员身份、CSRF 授权时**返回一次明文**，用于设备初次配置；存储、列表接口不返回明文。密钥重置使旧值失效。任何日志不记录 secret。
- 飞书/公网等远程部署不在本补丁范围。当前监听默认回环地址；任何跨主机手表协议必须**先建立认证的 TLS 通道**，不可将 `SUINING_BIND_ADDRESS=0.0.0.0` 作为安全公网配置。
- V3 的 Java Flyway migration 与 V1/V2 相同由 `DatabaseMigrations` 预先备份 H2 文件库；版本升级后**不可用旧应用原地降级读取**。回滚必须停止软件、恢复升级前 ZIP 备份、再使用旧版本，详见 `docs/runbooks/backup-restore.md`。
- 输入不合规的遗留密钥使升级**失败并停止启动**，避免静默丢失现有设备鉴权能力。排查、重置必须在受控离线备份环境进行。
- 本补丁不解决请求重放：后续需设计 `timestamp + nonce + HMAC` 或短期签名会话，与时间同步/协议版本管理配套，不可把摘要直接作为新的上行密钥。

## 验收

1. V1 数据库升级至 V3 后原设备密钥仍能登录，库中不出现明文；二次启动不重新哈希。
2. 新设备创建/重置返回明文一次，但持久化结果是摘要。
3. 篡改 secret 与短演示密钥不能登录。
4. 旧备份恢复保留原密钥和原记录；未来版本仍拒绝降级。
5. 仅在以上测试和 CI 成功后合并；本 PR 依赖 PR #1。
