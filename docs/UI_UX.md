# UI / UX 设计与验收契约

本文件定义岁宁 `preview` 分支的界面设计约束。它不是视觉风格说明书，而是维护者修改页面时必须守住的可用性、可访问性与照护语义底线。

## 1. 设计目标

优先级从高到低：

1. 用户能完成照护任务；
2. 用户能理解当前状态和下一步；
3. 老年用户、家属和管理人员在大字/窄屏下仍能完成任务；
4. 错误不会被静默伪装为正常；
5. 视觉保持克制、清晰、稳定；
6. 最后才是装饰性美化。

## 2. 用户与场景

### 管理员

高频任务包括老人建档、监护人维护、设备绑定、异常处置、阈值、公告、评论与邀请码。

特征：信息密度较高，需要快速扫描和批量管理，但不能牺牲错误确认。

### 家属

高频任务是查看健康、活动、位置与公告。

特征：更偏移动端/窄屏，阅读优先，功能入口应少而明确。

### 老年相关使用环境

即使主要操作人不是老人，也应假设存在：

- 视力下降；
- 精细指向能力下降；
- 对技术术语不熟悉；
- 焦虑状态下操作；
- 屏幕缩放/大字；
- 较低分辨率设备。

## 3. 尺寸与可读性

### 交互目标

- 主要按钮、关键导航、提交动作：目标尺寸 **≥48×48px**；
- 辅助按钮、图标按钮、链接式操作：**≥44×44px**；
- 不通过“图标看起来大”代替真实 hit area；
- 相邻危险/普通操作必须有足够间距，避免误触。

自动 UI smoke 当前把所有可见 focusable/interactive target 的 44px 作为硬门槛。

### 字号

- 正文不低于当前 16px 基线；
- 重要数据、标题和主要 CTA 应形成明显层级；
- 辅助说明可以弱化颜色/字重，但不能小到需要放大页面才能读；
- 大字模式应放大核心阅读内容与控件文字，而不是只放大标题。

## 4. 大字模式

大字模式是功能模式，不是主题装饰。

必须保证：

- 核心按钮仍可见；
- 表单 label 不被截断；
- 对话框可以滚动但不能把确认按钮挤出不可达区域；
- 表格在无法容纳时转为更合适的卡片/堆叠结构；
- 不通过隐藏重要字段维持排版；
- 390×844 下仍能完成登录和家属主要查看任务。

## 5. 响应式基线

长期视觉验收矩阵：

| 模式 | Viewport | 用途 |
| --- | ---: | --- |
| Admin desktop | 1440×1000（现有登录截图）/ 1360×900（Electron 默认） | 主桌面 |
| Compact desktop | 1024×768 | 小屏笔记本 |
| Family mobile | 390×844 | 家属窄屏 |
| Minimum window | 360×560 | Electron 最小窗口 |
| Large text desktop | 1360×900 | 大字桌面 |
| Large text mobile | 390×844 | 大字窄屏 |

新增核心页面应逐步进入以上矩阵。

## 6. 页面状态必须完整

每个核心任务页都应考虑：

- **loading**：用户知道正在发生什么；
- **empty**：说明为什么没有内容，以及下一步；
- **error**：说明用户可以做什么；
- **normal**：正常业务状态；
- **long-content**：超长名称、备注、公告、列表；
- **destructive-confirmation**：删除/解绑等明确对象和后果。

禁止：

- 空白页面代表 loading；
- 网络错误显示成“暂无数据”；
- API 失败后保留旧数据却不给“数据可能过期”的提示；
- “没有上报”显示成“正常”。

## 7. 状态、颜色与健康语义

颜色不能是唯一信息通道。

例如：

- 告警：图标/文本 + 颜色；
- 正常/异常：必须有明确文字；
- 不在线/未知/无新数据必须区分。

健康数据文案原则：

- 显示“最近一次成功上报时间”；
- 数据过旧要明确提示；
- 不把设备读数直接写成疾病诊断；
- 超阈值可以写“超过已设置范围”“建议关注/核实”，不要无依据写“患有…”；
- 无数据是“暂无新记录”，不是“健康正常”。

## 8. 表单

- 每个输入都有可见 label；
- placeholder 不能代替 label；
- 错误信息靠近对应字段；
- 表单整体错误使用 `role=alert` 或等效语义；
- 手机号、密码等设置正确 autocomplete/inputmode；
- 密码显示按钮有可访问名称和 pressed 状态；
- 提交过程中防止重复提交；
- 后端错误不能只显示“失败”，应给可执行下一步。

## 9. 键盘与焦点

必须：

- Tab 顺序符合视觉与任务顺序；
- `:focus-visible` 清晰可见；
- 所有鼠标动作存在键盘路径；
- 对话框打开后焦点进入合理位置；
- 对话框关闭后焦点回到触发元素；
- 不使用正 tabindex 人工重排焦点；
- Escape 的关闭行为只用于不会导致数据丢失的场景，或先确认。

## 10. 对话框与危险操作

危险操作必须说明：

- 要操作哪个对象；
- 会发生什么；
- 是否可恢复；
- 用户确认按钮使用具体动词。

差：
“确定吗？”

好：
“解绑设备 SN-123 后，该设备将停止向王奶奶档案上报。确定解绑？”

危险按钮不要与主要安全操作同色同权重。

## 11. 表格与窄屏

桌面表格适合管理扫描，但窄屏不应只是缩小字体。

优先策略：

1. 保留最重要字段；
2. 行转卡片；
3. 次要信息折叠；
4. 操作集中到明确菜单/按钮；
5. 保持对象名称和状态始终可见。

不要在 390px 宽度强行保留 8 列表格。

## 12. 导航

- 管理员和家属的信息架构保持角色一致性；
- 当前页面有明确选中态；
- 页面标题与导航术语一致；
- 不因 UI 美化改变业务名词含义；
- 返回/关闭行为可预测。

## 13. 图标

- 图标只承担辅助识别，不承担唯一语义；
- 只有图标的按钮必须有 `aria-label`；
- 新图标保持现有克制线性/简洁风格；
- 不为“统一”而替换已稳定、已验收且语义清楚的图标；
- 装饰性图片用空 alt/aria-hidden，信息图片提供实际描述。

## 14. 动效

- 动效用于解释层级/状态变化，不用于拖慢任务；
- 尊重 `prefers-reduced-motion`；
- loading 动画不阻止用户理解当前动作；
- 自动测试截图应关闭或固定非确定性动画。

## 15. Design Token 演进

当前 `commercial.css` 已承载大量稳定视觉规则，不进行一次性重写。

后续按以下顺序拆分：

```text
tokens.css
  颜色 / 字号 / spacing / radius / shadow / motion / focus / status
element-theme.css
  Element Plus 统一覆盖
accessibility.css
  focus / reduced motion / large text / assistive states
commercial.css
  页面布局与当前遗留规则（逐步变薄）
```

规则：

- 新的跨页面 magic value 优先成为 token；
- 不为单个页面建立新的“第二套设计系统”；
- 重构 CSS 时视觉变化和结构变化尽量分开提交。

## 16. 自动验收

当前 `.github/workflows/ui-quality.yml`：

- 用真实 Chrome 渲染生产 build；
- Accessibility Tree 检查关键控件/标题名称；
- 检查可见交互目标 ≥44px；
- 检查普通移动端与大字移动端；
- 与 `docs/screenshots/login-desktop.png` 进行粗粒度视觉差异比较；
- 上传证据截图。

视觉差异门槛不是“像素完全一致”。当前粗粒度 RMSE 用来抓布局/资源/字体等明显回归，不能替代人工视觉审查。

## 17. 视觉基线更新规则

只有以下情况允许更新基线：

1. 变更是明确预期；
2. 新截图在目标 viewport 下人工检查；
3. a11y 和交互没有倒退；
4. PR 描述解释为什么视觉变化合理。

禁止：

- CI 失败后直接覆盖 baseline；
- 自动接受新截图；
- 用提高阈值隐藏真实布局回归；
- 同时大改页面结构和 baseline，却没有前后对照。

## 18. UI PR 检查表

提交前确认：

- [ ] 主要任务是否更容易完成，而不只是更“漂亮”；
- [ ] loading / empty / error 是否有明确语义；
- [ ] 桌面、390px 窄屏和大字模式是否可用；
- [ ] 交互目标是否达到 44/48px；
- [ ] 键盘 focus 是否可见；
- [ ] 图标按钮是否有可访问名称；
- [ ] 状态是否不只靠颜色；
- [ ] 危险操作是否说明对象与后果；
- [ ] 健康数据是否说明时间/新鲜度；
- [ ] UI Quality 是否通过；
- [ ] 若更新视觉基线，是否人工确认并解释。

## 19. 下一阶段覆盖顺序

自动化从公共入口逐步扩展：

1. 登录 / 首次设置；
2. 管理端首页；
3. 老人建档；
4. 设备登记/绑定；
5. 告警/异常处理；
6. 家属首页；
7. 健康详情；
8. 邀请码和公告；
9. destructive flows；
10. Electron 安装态真实窗口。

每新增一条主流程，优先使用固定 fixture，避免测试依赖真实短信、真实设备或公网服务。
