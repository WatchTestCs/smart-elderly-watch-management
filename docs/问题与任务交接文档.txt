# TASK-02 · P0
## 从合成闭环推进到真实渠道和人工接手验收

### 已完成

已经基于现有 PR #27 集成回执幂等与 ADMIN duty 约束，没有另起一套平行实现。

| 场景 | 本次结果 |
|---|---|
| 同一 SOS requestId 重发 | 不重复创建事件 |
| 实际 HTTPS 请求超时、网关已接收 | 后续签名回执可收敛 |
| 重复/晚到回执 | 幂等，不重复审计；旧 worker 不能覆盖 delivered |
| 发送中强制终止 app/worker | 重启后等实际 2 分钟租约恢复，供应商幂等接受一次 |
| 网关 429/5xx/网络断开/DNS | 持久任务保留，分类错误与退避得到验证 |
| 无人接单 | 按原始期限升级 |
| 接单后无人处理 | 原始审计显示 acknowledge 后 614.111 秒升级，未伪造处理成功 |
| 同人处置并复核 | 被禁止；另一个授权 actor 才能 verify |
| delivered 但未接单 | UI 回归继续显示未接手 |

完整 HTTP 回归测试保留了：

`设备 SOS → MySQL 持久化 → outbox → TLS gateway → signed receipt → delivered → acknowledge → start → resolve → 第二个 actor verify`

以及对应审计事件。

### 任务

下一步接入专用 staging、真实测试手表、受控供应商测试渠道以及明确同意参与的值班人员。

1. 使用测试账号与测试联系人建立设备归属、家属和照护职责。
2. 核对供应商真实渠道的 accepted/sent/delivered 回执含义、签名与幂等协议。
3. 重新执行超时、回执重试、网络断开、worker 崩溃和恢复。
4. 记录真正的渠道送达、人员看到、接单、处置和独立复核时间。
5. 核对数据库、审计事件、前端展示以及接收端记录的一致性。

### 最重要的语义

始终保持：

`received ≠ sent ≠ delivered ≠ acknowledged ≠ resolved ≠ verified`

并明确：

`receiver_accepted ≠ human_acknowledged`

本机 receiver 返回 2xx 只证明该接收进程接受事件，不能证明真人收到、接手或完成救援。

### 验收标准

留下真实设备、真实渠道及两名独立授权人员参与的完整轨迹，分别量化持久化、送达、接手、处置和复核时延，并保留超时升级及备用救援流程的证据。

# TASK-04 · P1
## 保持有界限流，并补齐跨 ingress 与生产容量边界

### 已完成

进程限流已增加 32 shard 下的总预算：

- 默认最多 8192 active key；
- 默认最多 262144 时间戳槽；
- 拒绝新增/扩容，保留活跃配额，有限扫描过期 entry；
- 后台回收与 key/slot 高水位、容量拒绝指标；
- 每请求只锁对应 shard，未退回全局请求锁。

可信代理仅接受配置 CIDR 内的 TCP peer；Forwarded/XFF 有长度/hops 限制，从右向左处理可信链，直接伪造 XFF 无效。审计与登录使用同样的 IP 解析策略。

Nginx shared zone 覆盖同 ingress 后的多个应用副本；共享 MySQL 登录审计提供账号+IP 和账号级窗口，没有为所有普通请求新增数据库限流写入。

### 压测证据

| 项目 | 已验证范围 |
|---|---|
| 高基数 | 三波累计 300000 模拟来源 |
| 并发 | 256 goroutine；另有 race 回归 |
| 地址 | IPv4、IPv6、规范化及伪造代理链 |
| 共享来源 | 高频单 IP、NAT、trusted proxy、forged XFF |
| 状态上限 | 活跃 key 停在 8192；容量拒绝 291808 次 |
| 内存 | Windows GetProcessMemoryInfo 采样，微压测 RSS 峰值约 23.09 MiB |

上述为 limiter microbenchmark；不是 HTTP 吞吐、staging 容量或生产 RSS 上限。

### 任务

1. 多 ingress/多宿主部署时配置上游统一网关或 WAF 共享配额，不能把单进程 limiter 当全局配额。
2. 验证客户端不能绕过 ingress 直连公开后端，审查 TRUSTED_PROXY_CIDRS 的最小范围。
3. 在真实 NAT 分布、慢请求、持续来源轮换和后台任务下验证拒绝行为、误伤与 tail latency。
4. 给整个应用配置合理的请求并发、容器内存预算和高水位告警；limiter 状态预算不覆盖其他内存。

### 验收标准

持续高基数输入不能使 limiter 保留状态无界增长；多入口下的关键额度仍统一生效，正常 NAT 用户和可信代理识别正确，并提供实际环境、来源分布、RSS 与拒绝记录。

文件位于 `docs/reliability/data-classification.csv`、`projection-and-assets.csv` 和 `data-protection.md`。

新增版本 keyring，分离加密 key 与 lookupKey；新密文认证 key ID 与 scope，限制 reader 数量。

测试已经验证：

`key A 数据 → B 写入 → A 老数据可读 → B 重封装 → 删除 A 后可读`

以及错误 key、缺失 key、错误 scope、key ID 篡改时失败关闭。坐标解密失败不会把密文当正常坐标返回。

### 当前问题

仍不能声称全库加密。姓名、电话、地址、原始健康样本、生成列、围栏/事件、自由文本、部分历史明文与备份仍有待治理范围。

旧单 key 同时承担加密与 HMAC；历史 recipient_key 还可能是未配置 key 时的 SHA 回填。直接换 lookupKey 会改变去重/唯一索引及登录审计摘要。

### 任务

1. 对真实历史数据库与备份盘点明文、A/无版本密文、旧摘要和失败解密数量。
2. 为手机号制定规范化 + scoped HMAC lookup + AEAD 的扩列、双写、回填、唯一性校验与切读计划。
3. 旧 HMAC 索引采用停写迁移或有期限双读，保留登录限流旧窗口，不能直接换 C。
4. 健康 JSON、生成列、统计和范围索引先设计受控计算/投影边界，不能直接整体加密后破坏查询。
5. 分批重封装时用版本/CAS 防止覆盖并发修改；同步覆盖 change、归档、PG、重放队列与历史导出。
6. 所有副本先支持 A+B 读取，再切 B 写；最旧保留备份仍需 A 时保持离线受托保管。

### 验收标准

在生产结构与代表性历史数据的隔离恢复环境，证明所有依赖 A 的在线数据、回滚版本与备份均已处理，才允许退役 A。保留索引迁移、并发、唯一性、审计和恢复记录。

**keyring 原语通过，不代表真实旧数据库已经完成全量安全轮换；禁止自动生成替代 key 后继续运行。**

- 目录行锁、引用检查、先提交 deleting 墓碑再物理删除；
- 默认 dry-run、至少 24 小时宽限的 orphan GC；
- 阻止 GC 的备份租约及引用检查工具。

S3 模式要求共享 MySQL 与配置密钥；本地兼容模式仍需明确 key 配置和历史明文范围，不能把兼容旧图读取描述为旧图已加密。

双实例和实际恢复测试已经通过：

`A 上传 → B 读取 → A 下线 → B 继续读取`

`真实 MySQL dump + blob → 删除测试库/对象 → 恢复 → 全引用与 hash、SOS、outbox、session 核对`

匿名对象 GET 被拒绝。测试使用真实 SeaweedFS S3 兼容服务，并不构成所有供应商对象存储的认证。

### 任务

1. 旧 IMAGE_DIR 切 S3 前，受控停写/备份并盘点四处数据库图片引用。
2. 读取和验证旧明文/旧密文，按受控方案加密写对象、回填目录并核对全引用。
3. 当前没有自动复制历史图片目录的迁移命令，后续需实现或提供受审核迁移程序，不能只改 BLOB_BACKEND。
4. 生产备份持有 GC 租约，MySQL 一致快照后复制不可变对象集合/引用集；长任务必须在租约过期前续期。
5. 续期失败、对象缺失或 hash 不符应判备份失败；备份加密 key 与备份包分离保管。
6. 在多宿主、实际供应商和生产数据规模下验证一致性、恢复、权限、对象保留策略与 RPO/RTO。

### 回滚限制
