# 2.0.6 性能改造与对比

基点：`df606ec9000b6c8bfdbfd8932f3017331f78e00d`。日期：2026-10-20。本次针对实际发现的健康写入、规则查询、SQL 适配、通知调度瓶颈；没有改变告警业务、下行协议或 DeviceType 传值，没有编译商业反编译代码。

## 同数据规模的前后对比

环境：Windows、本机 Ryzen AI 9 H 365（10 核/20 线程）、约 31.1 GiB RAM，Go 1.27.2、MySQL 8.0.46；客户端 Python 标准库，回环 TCP。每次只有一个应用实例，8 个并发客户端，后台 worker 和 JSON 请求日志均启用，单个已绑定模拟设备形成真实写入热点。

每轮从同一份 20,000 条模拟采样及变更历史的数据库快照克隆，随后固定预热两次请求。单条场景计时开始恰为 20,002 行，200 条场景为 20,400 行；新旧版本一致。每个场景执行两轮，第二轮反转版本顺序，每轮计划发送 15 秒，最后等待已发请求结束，吞吐分母包含收尾时间。计时期间没有并行运行 Go 测试或构建。写入越快，计时结束数据越多，未限制新版实际写入量。

| 场景，均为 8 并发 | 原版 | 本次 | 对比 |
|---|---:|---:|---:|
| 每请求 1 条：采样/秒中位数 | 517.06 | 601.15 | +16.3% |
| 每请求 1 条：每轮 P95 范围 | 17.373–24.235 ms | 16.026–22.375 ms | 存在机器波动 |
| 每请求 200 条：采样/秒中位数 | 905.61 | 8,880.25 | 9.81 倍 |
| 每请求 200 条：每轮 P95 范围 | 2,067.860–2,174.311 ms | 486.579–529.572 ms | 明显下降 |
| 每请求 200 条：每轮 P99 范围 | 2,087.097–2,224.883 ms | 720.068–1,005.349 ms | 明显下降，尾延迟仍存在 |

这里的 8,880 是**采样条数/秒**，不是 HTTP 请求/秒；对应约 44.4 请求/秒，每请求 200 条。不是拿不同 batch size 的数值互相比。两个样本的中位数是两轮数值的均值；P95/P99 列出逐轮范围，没有把分位数冒充合并分位数。全部计时请求均校验 HTTP 状态、业务码、accepted 数量、duplicates=0，并按运行 ID 查询 `health_sample` 和 `health_change`，两张表都与请求数×batch size 相等。

原始八轮数据、运行 ID、各分位数与核对行数：[performance-2.0.6.json](verification/performance-2.0.6.json)。此前探索轮次不用于此表。

MySQL 两侧均保持 `innodb_flush_log_at_trx_commit=1`。本机测试实例两侧均未开启 binlog；这是共同的实验环境设置，不是本次加速措施。没有降低提交持久性、关闭索引、关闭日志、跳过认证、丢弃变更历史或提前返回成功。生产 binlog、复制、网络、HTTPS 及机器差异会改变结果。

## 具体修改

### 真正批量写入

`backend/internal/health/store.go` 新增 `SaveBatch`；`handler_health.go` 使用它。每批仍最多 200 条，先规范化，锁住原有 revision clock，再批量读取现有版本，按输入顺序计算更正、重复、过期版本与新 revision，合并最终采样行，但为每个有效中间版本保留独立变更事件。

原来 200 条通常执行约 1,200 条健康存储 SQL，现为 6 条：锁时钟、读取已有版本、更新时间钟、写最终样本、写全部变更历史、失效日缓存。设备认证、绑定锁和在线时间更新仍在外围事务里；最终 HTTP 成功仍在事务提交之后。全为重复/过期记录时不写时钟和变更历史。

日统计失效仍覆盖该老人的全部缓存日，未用缩小范围换性能；同批只做一次失效，因为整个事务本来就是原子可见。若某一条同版本不同内容，整个批次拒绝并回滚。`Save` 单条入口复用相同逻辑，旧调用者继续兼容。

### SQL 结构缓存

`backend/internal/db/database.go` 缓存 SQL 方言转换结果和参数位置，最多 512 项，FIFO 淘汰。缓存不保存参数值、连接、查询结果或个人数据；每次调用重新构造绑定参数，仍走驱动参数化执行，不拼接用户数据。

`BenchmarkMySQLHealthWriteQuery` 在同机三轮结果：原来约 59,969–64,138 ns/op、约 14 KiB、63 allocs/op；本次约 76.74–90.98 ns/op、224 B、1 alloc/op。这是 SQL 适配微基准，不能称为 HTTP 提升数百倍。并发参数隔离、引用字符串、重复参数、缺参和淘汰后重编译另有行为检查。

### 规则窗口索引

`0006_health_performance.sql` 增加 `idx_health_rule_window(old_id,device_id,metric,deleted,sample_start,revision)`，支持每指标最新样本查询和基线时间窗筛选，避免为查不到的步数扫描同老人所有心率。

实际探索查询计划：原版缺失步数查询扫描约 25,259 行，约 57.4 ms；加索引的查询使用反向范围扫描，返回空范围约 0.0196 ms。两次探索时总行数不同，因此不据此宣称精确倍数；回归检查另在相同 1,000 条无关心率数据上确认：原版扫描约 1,000 行，新版选择专用索引，估计扫描不超过 10 行。没有修改指标来源、时间窗、个人基线阈值、绑定条件或采样上限。索引有额外写入维护成本，单独加索引的探索轮写吞吐未见明确提升；其直接收益是减少查询扫描。总表反映累计改造，不能把所有收益归给索引。

### 就绪通知队列连续处理

公告 worker 原先每秒只取一条；照护 worker 每 5 秒只取一条。改为每轮连续、串行处理最多 128 条公告/站内任务和 32 条照护任务；空队列立即停止，定时器负责后续轮询。外部调用仍在数据库领取事务之外，保留 SKIP LOCKED、租约、幂等键、重试退避、渠道耗尽和签名回执。

网络预算不足以容纳客户端超时及数据库收尾时，不领取下一条外部通知，避免剩余几秒的周期留下无谓的过期租约。没有增加并发轰炸网关；真实供应商吞吐和配额未量测。模拟站内队列回归：原 worker 在 10 秒内仅处理 10/120 条，新 worker 本次用约 751 ms 处理完 120 条（不含建库和入队）。具体耗时见本地测试记录，不把站内记录可用解释成家属已读或短信到达。

压测脚本每条记录含唯一运行 ID，校验 accepted 和 duplicates，输出请求吞吐、采样吞吐和分位数。严格复现须先给新旧版本恢复同一份隔离库快照，固定预热请求数，并核对两张健康表的运行 ID 行数；不能在持续增长的同一库里任意先后运行后声称同规模对比。

新增检查覆盖：同批重复、过期和多次更正、中间版本历史保留、冲突原子回滚、缺失指标查询计划、并发参数不串用、有界缓存淘汰、突发队列处理和不足网络预算不领取。原有提交顺序、绑定隔离、日统计更正/删除、鉴权、通知租约/降级等检查继续运行。本机完整结果另见 `verification/performance-tests.json`。CI 集成测试上限从 240 秒调整为 600 秒，因为已有完整 handler 套件本机曾耗时约 249 秒；这不是产品性能数据。

未量测/未运行：生产机器、真实设备和通知网关、跨机扩容、分析副本吞吐、持续数小时稳态、混合读写流量、Go race（实际尝试后因 CGO 未启用而未能执行；本机未配置 C 编译器），本轮也没有验证容器整套启动。两轮短测不构成容量承诺，也不足以证明所有接口已经达到极限。

## 迁移和回滚

本次只新增索引，没有新增业务字段。商业包对该索引/内部批量实现 **包内无出处**；定义出处是本次 `0006_health_performance.sql`、`health/store.go` 和 `db/database.go`。原迁移 0001–0005 未修改。

备份并安排索引构建窗口后启动新版，由迁移器应用 0006。大表建索引会消耗 I/O 和元数据锁，实际耗时需要在目标数据副本预演。回退新版代码可保留这个兼容索引；确需回滚 DDL 时停写，执行 `migrations/rollback/mysql_0006_health_performance.sql`，只移除该索引和对应迁移记录。若继续回退平台 0005，应先回滚 0006，再遵循原平台密钥/备注解密及导出流程。

## 仍有的边界

全局 `health_clock` 保证提交顺序与增量游标不漏数，因此仍会串行化写入；同设备事务锁也继续排除并发换绑。直接删除这些锁，或者先返回成功再异步落库，都不符合本项目当前语义。本次缩短了锁内工作量。个人基线仍读取所需历史有效样本，日统计仍可能在持锁期间计算大窗口；继续消除这类上限需要另行设计按老人修订号/一致性快照或聚合模型，并验证现有游标兼容性，不能把它当作无风险开关。
