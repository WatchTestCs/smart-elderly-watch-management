# 手表安全凭据与队列存储

## 决策与威胁边界

P1-12 要求断网和重启后恢复设备凭据及离线队列，同时避免 Preferences 文件泄露健康记录。
使用 HarmonyOS HUKS 保存应用作用域的 AES-256 密钥，应用只持有别名，不调用密钥导出。
每次写入用系统安全随机数生成新的 12 字节 nonce，AES-GCM 认证标签为 16 字节，
AAD 固定为本应用快照协议标识。封装版本、nonce 与密文可公开，设备凭据和健康/SOS 内容不可公开。

接口依据为[官方 HUKS 加解密指南](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/huks-encryption-decryption-arkts/)
和[HUKS API](https://developer.huawei.com/consumer/en/doc/harmonyos-references/js-apis-huks/)。
使用 API 18 兼容范围内的接口；安全随机数能力缺失时拒绝保存，不能用 Math.random 或明文替代。
HUKS 所在设备的实现及隔离能力应实际验证，不能仅凭调用了 API 宣称已证明硬件安全等级。

此设计保护离线文件与跨应用密钥访问边界，不保护已被控制的应用进程、系统 root、
显示中的健康数据或已授权使用手表的人。不将密钥导出到备份；只恢复密文而丢失 HUKS 密钥时应停止恢复，不能自动生成新密钥覆盖记录。

## 一致性与生命周期

- 一个密文快照包含配置、按服务器和设备号隔离的认证凭据、采样、SOS、模拟计数及 ID 序列。
  凭据只在服务端登录确认后保存；修改服务器/设备时不会读出另一身份的已存凭据。
- `WatchStore.open` 异步解密后才允许同步读取和持久化。组件退出时使未完成的初始化结果失效，避免隐藏页面被旧初始化回写。
- HUKS 按 16 KiB 分段处理完整快照；认证完成前不返回任何解密片段，失败时 abort 并清理临时字节缓冲。
  允许完整 200 样本队列，整体明文上限 1 MiB；超限拒绝写入，不淘汰旧记录。
- 保存期间拒绝第二次写入；一次写入或 flush 的完成状态不明时封锁当前实例，必须真正重载。
  不凭异常断定“没有写入”。重载读取已落盘的快照；原有 recordId、bindingVersion 和 SOS requestId 保持不变。
- 收到上传确认后才清除采样；记录 SOS 确认后继续保留其 requestId，丢 ACK 不会重新创建同一次求助。
  忘记凭据不清除健康记录或求助历史，不改变服务端凭据，撤销设备须由管理员操作。

Preferences 是单进程存储，不应从多个进程或多个独立 Store 实例同时写同一份文件。
当前 UI 使用一个 Store 与串行操作；后续自动调度必须复用该实例和串行操作边界。

## 旧明文迁移和故障处置

1. 读取旧版存在的键，保留缺省值语义；生成密文，先写入 `encryptedStateV1` 并等待 flush 成功。
2. 仅在密文落盘确认后删除旧明文键，再次 flush。若第二步中断，重启优先解密已提交副本，再完成清理。
3. 密文已存在但校验失败、版本不支持或密钥不可用时，保留文件并阻止操作；即使旧明文仍在，也不回退读取它。

不得把清除应用数据当作修复方法，这会丢失未确认求助/采样。应先保全应用文件及设备状态，由管理员确认密钥和备份处置。
迁移成功后旧软件不能读取新密文格式，不支持直接降级回旧版；升级/回滚部署必须考虑这一数据边界。
删除明文键不等价于证明文件系统历史块、系统备份或已有外部副本已被安全擦除，这些副本另按保留与清退制度处理。

## 分层验证

- Node 层使用生产 WatchStore、EncryptedPreferences、WatchVault；只有 SDK 边界由真实 Node AES-GCM 适配。
  覆盖满队列、UTF-8 分段、篡改、错/丢密钥、能力缺失、两阶段迁移、写入确认丢失、重启及凭据作用域。
- 真实 Go/MySQL E2E 从磁盘密文恢复生产 Store 与凭据，在提交后断开真实 HTTP 连接，再重试并核对后台去重。
  其 Node HUKS 适配器不能算作设备 HUKS 验收。
- SDK 构建、模拟器真实 HUKS 初始化/重启、界面队列与 SOS 恢复各自保留源码 SHA、HAP 摘要与结果。
  本文是设计和验收入口，不是所有层次都已通过的证明。
